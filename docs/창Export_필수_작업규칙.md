# 창Export 필수 작업 규칙

## 1. 목적과 참고 기준

창Rebar·창BIM의 사용자 변경 통제 및 검증 원칙을 창Export의 현재 프로젝트 구조에 맞게 정리한다. 반복되는 선언은 줄이고, 문제 접수에서 승인·검증·배포까지의 판단 기준을 명확히 한다.

2026-08-31에 확인한 참고 자료:

- `C:\Users\user\Desktop\창Rebar\AGENTS.md`
- `C:\Users\user\Desktop\창Rebar\docs\GIT_이력관리_규칙.md`
- `C:\Users\user\Desktop\창BIM\AGENTS.md`
- `C:\Users\user\Desktop\창BIM\ChangBIM-Git\AGENTS.md`
- `C:\Users\user\Desktop\창BIM\ChangBIM_필수_작업규칙.md`
- 마지막 문서의 `ChangBIM-Git\docs\archive` 사본은 SHA-256이 동일하다.

적용 시 정리한 차이:

- 창BIM의 현재 운영 방식을 따라 문서만 변경하면 DLL을 빌드하지 않는다.
- 창Rebar 문서의 예약 점검 일정은 도입하지 않는다. 창Export는 요청 없는 예약 실행을 금지한다.
- 과거 창BIM의 버전별 폴더 복사 방식 대신 로컬 Git 커밋·태그와 고정 최신 배포 폴더를 사용한다.
- 철근 정착·이음, 물량 산출 및 시스템비계 전용 형상 규칙은 복사하지 않는다. 창Export에는 모델 보존과 실제 DWG 출력 결과 검증을 적용한다.
- 이름 기반 분류를 일괄 금지하지 않는다. 창Export의 Type/Parameter Rule은 명세상 필요한 기능이므로 사용자 설정에 근거해 평가하고, 임의 이름 필터를 추가하지 않는 것으로 구분한다.
- 원본 프로젝트의 Git 주소, 태그 번호, 설치 경로 및 자동화는 참고 정보이지 창Export 실행 지시가 아니다.

## 2. 문제 보고와 변경 승인

### 기본 상태

- 문제 보고·질문·불편 표현을 받으면 먼저 읽기 전용으로 확인한다.
- 스크린샷, 오류 로그, 테스트 실패와 원하는 결과 설명은 변경 승인이 아니다.
- 사용자의 강한 표현을 승인이나 작업 범위 확대의 근거로 삼지 않는다.
- `로직 수정하지 마세요`가 있으면 UI나 설정을 바꾸는 방식으로 우회하지 않는다. UI만 변경하라는 명시적 요청이 함께 있으면 UI만 허용한다.
- 보류된 기능은 다음 대화에서도 보류 상태로 유지한다. 과거 개발계획에 포함됐다는 이유로 자동 진행하지 않는다.

### 요청별 처리

| 요청 | 허용 범위 | 하지 않는 일 |
|---|---|---|
| 왜 그런지, 확인·검토·진단 | 파일·로그·Git 이력 읽기와 설명 | 파일 수정, 최신빌드 갱신, 커밋 |
| 로직 수정 금지, 일단 구축만 유지 | 현재 상태 보존과 설명 | UI 개선을 포함한 임의 기능 변경 |
| 개선사항으로만 추가 | 대화 안에서 문제와 증거 정리 | 승인 없는 MD·README·코드 기록 |
| 문서를 만들어 달라 | 명시된 문서 작성·검증·로컬 기록 | 소스·설정·DLL 변경 |
| UI만 수정 | 승인된 배치·표시·조작 요소 변경 | 분류·수집·저장·Export 결과 변경 |
| 테스트만 실행 | 요청된 검증 실행과 결과 보고 | 실패를 이유로 한 자동 수정 |
| 로직 수정·기능 구현 | 승인한 동작과 필요한 검증 | 무관한 개선·리팩터링·기능 추가 |

### 소규모와 대규모 변경

- 한두 가지 UI·로직 문제는 원인과 영향 범위를 먼저 정리하고 진행 여부를 재확인한다. 최종 승인된 동일 범위를 계속 재확인하지 않는다.
- 재확인 시 변경 대상, 유지할 동작, 필요한 테스트와 로컬 기록 여부를 짧게 설명한다.
- 명확한 문서 작성 요청을 받았으면 그 문서 범위에서 진행할 수 있다. 문서를 만드는 권한은 애드인 로직 수정 권한이 아니다.
- 하나의 문제라도 여러 Category, 공통 Export 흐름, 저장 형식 또는 실제 DWG 품질에 영향을 주면 대규모로 취급한다.
- 누적 문제가 많거나 기억·회귀 범위가 불명확해지면 단계별 수정 또는 별도 기록을 제안한다. 제안만으로 구현하지 않는다.
- 예상보다 범위가 커지거나 사용자 데이터 손상 위험이 나타나면 안전한 상태에서 멈추고 추가 승인을 요청한다.

## 3. 분석 및 대기 목록

- 각 항목의 현상, 재현 조건, 확인된 증거, 원인 후보, 영향 범위와 승인 상태를 구분한다.
- 실제 데이터 누락과 화면 가림, 저장 실패와 표시 갱신 실패, 판정 오류와 DWG 반영 누락을 구분한다.
- 상태는 `보고됨 → 분석 중 → 분석 완료·수정 대기 → 수정 승인 → 구현·검증 완료`로 구분한다.
- 사용자가 일부 항목만 승인하면 나머지는 대기 상태로 남긴다.
- 대화에서 제안한 UI 용어나 버튼 배치가 사용자 확정 요구처럼 기록되지 않도록 한다.
- 파일에 문제 목록을 남기는 작업은 요청된 경우에만 수행한다. README는 별도 수정 요청이 필요하다.
- 명시적인 보류·중단 뒤에는 반복적으로 수정을 권유하거나 파일을 바꾸지 않는다.

## 4. 구현 범위와 사용자 데이터 보존

- 승인된 현상을 해결하는 최소 범위만 변경한다. 인접한 문제는 별도 항목으로 보고한다.
- 사용자 미커밋 파일은 보존한다. 정리·포맷·리팩터링을 명분으로 덮어쓰지 않는다.
- 기본값, 대상 Category, 정렬, 단위, GUID, 저장 키, 필터, 오류 처리 변경은 결과에 영향을 주는 로직 변경으로 취급한다.
- 데이터 부족을 임의 추정으로 보완하거나 실패를 정상 결과로 표시하지 않는다.
- 테스트를 통과시키기 위해 기대 결과를 실제 오류에 맞춰 낮추지 않는다.
- 새로운 SDK나 의존성은 기술·배포 필요성을 먼저 설명한다. 유료 서비스 이용이나 라이선스 계약은 임의로 진행하지 않는다.

## 5. 창Export의 화면·기능 설계 원칙

이 절은 향후 승인된 설계 변경에 적용하는 기준이며, 현재 UI나 미구현 기능을 수정하라는 지시가 아니다.

- 개발용 용어와 데이터 구조를 그대로 사용자 화면에 노출하지 않는다. 한국어 중심으로 목적과 조작이 이해되는 표현을 사용한다.
- 기술 검증용 명령과 일반 출력 기능을 구분한다. 기술 게이트의 구현 순서를 사용자 작업 순서로 오해하지 않는다.
- 개발 명세에서 수동 `CAD_LAYER`는 자동 분류의 예외 처리 수단이다. 모든 객체를 하나씩 선택해 지정해야 하는 흐름을 기본 전제로 삼지 않는다.
- `회사 CAD Standard` 문구, 선종류 자유 입력, 적은 기본 Layer 목록, Rule 입력 불편은 기존에 보고된 개선 후보이며 완료된 기능이나 승인된 변경으로 간주하지 않는다.
- 선택 가능한 값은 콤보박스·스크롤 가능한 목록 등으로 제안하고, 실제 목록의 출처와 사용자 추가 가능 여부를 구분한다.
- 기본 Layer 예제는 실무 전체 표준이 아니다. 샘플만 제공한 상태를 충분한 분류 체계라고 설명하지 않는다.
- Rule 추가 버튼뿐 아니라 Category·Parameter·비교 방식·값·Target Layer 입력, 우선순위와 결과 확인까지 사용 흐름을 검토한다.
- 추가·삭제·저장·취소의 의미를 구분하고, UI 변경 시 DPI·가림·스크롤·키보드 입력과 미저장 값 처리 등을 확인한다.
- 실제로 적용되지 않는 배치·후처리 옵션은 미지원 또는 미연결임을 명확히 표시한다.

## 6. Revit 및 DWG 기술 원칙

### 모델과 매개변수

- CAD 출력 때문에 원본 모델의 Family, Subcategory, Object Styles, View Template을 임의 변경하지 않는다.
- 공유 매개변수는 고정 GUID와 올바른 Instance Binding으로 다룬다. 같은 이름의 다른 정의를 안전한 동일 매개변수라고 가정하지 않는다.
- 사용자 Shared Parameter 파일을 덮어쓰지 않고, 임시 파일 사용 후 기존 경로를 복구한다.
- 읽기 전용·미지원·그룹·링크 요소는 원인을 구분해 보고한다. 실패한 적용을 성공 개수에 포함하지 않는다.
- 모델 변경은 Revit API가 허용한 문맥과 Transaction 안에서 수행하고 Undo·실패·취소 동작을 검증한다.
- 임시 View·Filter·Override를 사용하면 성공·실패·취소 시 원본 복구 및 임시 요소 잔존 여부를 확인한다.

### 분류와 실제 출력

- `CAD_LAYER` 저장, Rule 판정 미리보기, Native DWG 생성, 실제 DWG Layer Remap/Merge는 각각 독립적으로 검증한다.
- Native Export가 임의의 인스턴스 문자열을 바로 최종 Layer 이름으로 사용한다고 가정하지 않는다.
- Rule 우선순위·동률·빈 값·누락 Parameter·미정의 Target Layer의 처리 결과를 설명 가능하게 남긴다.
- UI상 분류가 맞다는 사실만으로 DWG Entity가 올바른 Layer에 포함됐다고 판단하지 않는다.
- Sheet별 DWG 생성, 그룹별 단일 파일, Model Space 평면화와 실제 1:1 배치는 서로 다른 결과다. 지원 여부를 혼용하지 않는다.
- 좌표·단위·축척·Viewport Clip, Text·한글 폰트·Dimension·Hatch·Block·Xref 등 변경에 관련된 항목을 검증한다.
- 범위나 경계 계산을 했다는 사실만으로 Sheet의 시각적 결과가 보존됐다고 판단하지 않는다.
- DWG 후처리는 정당하게 사용할 수 있고 재배포 조건이 확인된 SDK로만 구성한다. SDK 미연결 상태를 완료로 보고하지 않는다.

### 파일과 설정

- 사용자 Profile은 설치·업데이트·제거 과정에서 기본 보존한다. 기본 예제로 자동 초기화하지 않는다.
- 기존 DWG는 사용자 확인 없는 덮어쓰기나 실패 출력으로 손상시키지 않는다.
- 임시·검증용 파일과 최종 결과를 구분하고 부분 실패·경고·취소를 결과 로그에 남긴다.
- 원본 RVT를 테스트 목적으로 자동 저장하지 않는다. 실제 모델 변경 시험은 승인된 샘플 또는 사용자가 지정한 범위에서 수행한다.

## 7. 작업 종류별 검증

- 문서만 변경: 내용 일관성, 경로, 링크, 승인 범위, diff를 확인한다. DLL 빌드·패키징은 하지 않는다.
- UI 변경: 빌드 외에 실제 창의 배치·조작 검증을 수행하고, 실행하지 못했으면 미검증으로 보고한다.
- Rule·Profile 변경: 수동 우선, 자동 Rule, 기본 Mapping, 충돌·누락·비활성 항목 등 관련 사례를 확인한다.
- 모델 쓰기 변경: Transaction, Undo, 읽기 전용·실패 사례와 원본 보존을 확인한다.
- Export 변경: 실제 RVT/DWG로 변경 구간을 검사한다. 컴파일 성공과 실제 파일의 품질 검증을 구분한다.
- 설치·배포 변경: 스크립트 구문·참조 경로·DLL 해시를 확인한다. 설치 테스트가 실제 사용자 환경을 바꾸면 먼저 허락을 받는다.
- 실패한 검증은 숨기지 않는다. 테스트 실패를 해결하기 위해 승인 범위를 임의 확대하지 않는다.

## 8. 완료 보고

- 실제 변경한 항목과 변경하지 않은 항목을 구분한다.
- 수행한 검사, 빌드 결과, 실제 Revit·DWG 시험 여부와 남은 제한을 알린다.
- 검증 후 로컬 커밋과 태그를 보고한다. 문서만 변경했다면 설치를 요구하지 않는다.
- 새 설치본을 만든 경우에만 고정 설치 경로 및 DLL 해시 일치를 안내한다.
- 미래 개선 제안을 완료 보고에 섞어 이미 구현된 것처럼 표현하지 않는다.

Git 번호, 최신 배포본 및 원격 동기화의 구체적인 절차는 [Git 이력관리 규칙](GIT_이력관리_규칙.md)을 따른다.
