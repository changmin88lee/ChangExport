# 창Export Git 이력관리 규칙

## 1. 기본 위치와 적용 조건

- 저장소: `C:\Users\user\Desktop\창Export`
- 기본 브랜치: `main`
- 초기 소스 기준: 커밋 `6813e5d`, 주석 태그 `beta-0.1.0`
- 로컬 기록 작성자: `ChangExport Automation <changexport-automation@local>`
- 최초 구성 시 원격 저장소는 연결하지 않았다. 연결 또는 변경은 별도 사용자 요청으로만 수행한다.
- 현재 [AGENTS.md](../AGENTS.md)의 사용자 변경 통제가 Git 자동 기록보다 우선한다.
- 분석만 수행한 작업에서는 파일 변경, staging, 커밋·태그, 버전 변경 및 배포 갱신을 하지 않는다.
- 승인된 변경을 검증한 뒤에만 해당 작업 파일을 기록한다. 문서 작성 요청도 문서 범위의 로컬 기록을 포함한다.

## 2. 작업 이력 번호와 제품 버전

### 작업 이력

- 이 규칙 도입 작업부터 `V1`, `V2`, …의 연속 번호를 사용한다. 초기 `beta-0.1.0` 태그를 바꾸거나 V번호로 재해석하지 않는다.
- 코드·설정·문서 등 승인된 하나의 논리적 작업마다 번호를 하나 부여한다.
- 커밋 직전에 `git tag --list 'V*'`에서 정규식 `^V[0-9]+$`에 맞는 태그만 골라 숫자로 비교한다. 해당 태그가 없으면 `V1`부터 시작한다.
- 커밋 제목은 `V1 창Export 작업 규칙 정립`처럼 번호와 한국어 변경 요약으로 작성한다.
- 커밋 성공 후 같은 번호의 주석 태그를 생성한다. 다른 형식의 기존 태그는 보존한다.
- 번호 충돌이 있으면 최신 태그를 다시 확인하고, 기존 태그를 강제 갱신하지 않는다.
- 커밋은 성공했으나 태그만 실패한 경우 원인을 확인한다. 같은 작업의 중복 커밋을 만들지 말고 누락된 태그 생성만 안전하게 처리한다.

### 제품 버전

- 루트 `VERSION`은 설치본의 제품 버전을 나타내며, 현재 형식은 `Beta 0.1.0`이다.
- Git 작업 번호 `V###`와 제품 버전은 서로 다른 값이다. 문서 작업 때문에 DLL 버전이 바뀐 것처럼 제품 버전을 올리지 않는다.
- 문서 전용 작업은 `VERSION`, 프로젝트의 `Version`·`FileVersion`, 배포물과 기존 제품 태그를 유지한다.
- 새 제품 배포를 만드는 승인된 작업에서는 제품 버전, 프로젝트 메타데이터, 실행 화면·로그 등에 실제로 사용되는 버전값을 일치시킨다. 현재 값들이 자동 연동된다고 가정하지 않는다.
- 같은 제품 버전으로 서로 다른 DLL을 역사 배포본에 저장하지 않는다. 정식 배포 식별자는 제품 버전과 Git 작업 태그/커밋을 함께 기록한다.
- 제품 버전 표시를 연결하거나 빌드 스크립트를 바꾸는 작업 자체도 승인 범위 안에서만 수행한다.

## 3. 작업 순서

1. `AGENTS.md`와 작업에 관련된 상세 규칙을 읽고 요청·승인·제외 범위를 확인한다.
2. 현재 브랜치, `git status`, diff, untracked 파일을 검사하고 사용자 변경을 보존한다.
3. 승인된 변경을 구현한다. 분석만 요청받았으면 이 단계 이후를 진행하지 않는다.
4. 변경 종류에 맞는 검증을 한다. 문서만 변경했으면 문서 검사만 하고 빌드하지 않는다.
5. DLL에 영향을 주는 변경이면 Release 빌드와 관련 테스트를 수행하고 검증된 최신 설치본을 갱신한다.
6. 커밋 직전에 범위·비밀정보·산출물·충돌을 점검하고 다음 숫자형 V태그 번호를 정한다.
7. 실제 작업 대상 파일만 명시적으로 staging하고 staged diff를 확인한다. `git add .`로 사용자 변경을 함께 넣지 않는다.
8. 로컬 커밋과 주석 태그를 생성한다.
9. 작업 상태와 커밋·태그 연결을 확인한다. 남은 사용자 변경이 있으면 그대로 보존하고 보고한다.
10. 완료 내용을 보고한다. 별도 요청이 없으면 원격 Git 명령은 실행하지 않는다.

## 4. 검증과 커밋 중단 조건

- 코드 변경은 `dotnet build .\ChangExport.csproj --configuration Release` 및 관련 테스트로 검사한다.
- 문서·규칙만 변경했으면 링크·경로·규칙 충돌·오탈자와 `git diff --check` 등으로 검사한다.
- Markdown의 의도된 줄바꿈 공백처럼 기능상 필요한 형식과 실제 잘못된 공백을 구분한다. 원본 문서 전체를 임의 포맷하지 않는다.
- 빌드·검증 실패, 충돌, merge/rebase 진행 중, 비밀정보 의심, 승인 범위 밖 변경이 있으면 해당 작업 커밋을 중단하고 사유를 보고한다.
- 변경이 없으면 빈 커밋을 만들지 않는다.
- 저장소 정리를 이유로 사용자의 미커밋 파일을 버리거나 현재 변경을 되돌리지 않는다.
- 서로 무관한 사용자 작업을 한 커밋에 섞지 않는다. 완료·검증되지 않은 중간 상태를 통과한 기준선처럼 태그하지 않는다.
- 기존 커밋 amend, 태그 삭제·강제 이동, 강제 push, 이력 재작성은 하지 않는다.

## 5. 최신 설치본 관리

- 프로젝트: `ChangExport.csproj`
- 빌드 DLL: `bin\Release\net8.0-windows\ChangExport.dll`
- 최신 배포 폴더: `배포폴더\최신`
- 설치 안내 경로: `C:\Users\user\Desktop\창Export\배포폴더\최신\설치.cmd`
- 갱신 도구: 저장소 루트의 `Build-Latest.ps1` 또는 `Build-Latest.cmd`

검증 및 갱신 절차:

1. 현재 승인된 소스에 대해 Release 빌드가 성공했는지 확인한다.
2. `Build-Latest.ps1`로 최신 설치본을 갱신한다. 이 스크립트가 빌드까지 수행하는 경우 중복 빌드는 피한다.
3. `-SkipBuild`는 동일 소스의 빌드 성공을 확인한 경우에만 사용한다. 컴파일 실패를 우회하는 옵션으로 사용하지 않는다.
4. 빌드 DLL과 최신 배포 DLL의 크기 및 SHA-256을 비교한다. 필요하면 배포용 Data·설치 스크립트·제품 버전도 원본과 비교한다.
5. 설치 스크립트가 어느 DLL을 선택하는지 확인한다. 파일 시각이나 다른 위치의 오래된 DLL 때문에 설치 대상이 달라지지 않는지 검증한다.
6. 실제 설치, 제거, Revit 프로세스 종료·재시작은 별도 사용자 요청이 있을 때만 수행한다.

문서만 변경한 작업에서는 이 절차를 실행하지 않는다. 최신 배포 폴더는 설치용 고정 경로이며 역사 자료가 아니므로 승인된 새 설치본으로 갱신할 수 있다.

## 6. ZIP 및 보존 자료

- Git 이력만을 위해 `V1`, `V2` 같은 폴더나 소스 복사본을 만들지 않는다.
- 사용자가 ZIP 또는 정식 배포를 요청한 경우에만 새 패키지를 만든다. 매 작업마다 ZIP을 생성하지 않는다.
- 기존 역사 ZIP과 베타 패키지는 보존하고 같은 이름으로 덮어쓰지 않는다. 새 버전 패키지는 구별되는 이름을 사용한다.
- 압축 전 빌드 DLL과 설치 대상 DLL을 비교하고, 압축 후 ZIP 내부의 실제 설치 대상 DLL도 SHA-256으로 확인한다.
- 최종 ZIP을 만든 후 ZIP 자체의 SHA-256을 계산한다. ZIP 안 문서에 ZIP 자신의 최종 해시를 넣는 순환 기록은 만들지 않는다.
- 설치 패키지에 Revit API DLL, 사용자 RVT/DWG, 라이선스가 확인되지 않은 SDK 또는 비밀정보를 포함하지 않는다.
- Git에서 제외된 DLL·ZIP·RVT·DWG는 Git으로 복원되지 않는다. 이 파일의 별도 보존이나 외부 백업이 필요하면 사용자에게 설명하고 허락을 받는다.

## 7. 추적 파일과 제외 파일

- 추적: 애드인 소스, 프로젝트 파일, 설정 예제, 요구사항·작업 규칙, 설치·빌드 스크립트, 필요한 테스트 소스.
- 제외: 기존 `.gitignore`의 `bin/`, `obj/`, `배포폴더/`, 사용자 IDE 파일, `*.rvt`, `*.dwg`.
- 대형 바이너리가 필요해지면 추적 필요성·크기·개인정보를 먼저 확인한다. 요청 없이 Git LFS나 원격 바이너리 저장 방식을 도입하지 않는다.
- 비밀정보와 개인 설정을 커밋하지 않는다. 파일명뿐 아니라 diff 내용도 확인한다.
- `README.md`와 원본 개발 명세는 명시적인 해당 문서 수정 요청이 있을 때만 변경한다. 일반 커밋 기록을 위해 자동 수정하지 않는다.

## 8. 브랜치와 원격

- 현재 단독 작업의 기본 브랜치는 `main`이다. 범위가 큰 승인 작업을 분리할 필요가 있으면 기능·수정 브랜치를 사용할 수 있다.
- 브랜치 전환으로 미커밋 변경이 영향을 받으면 먼저 보존 방법을 확인한다. 요청받지 않은 rebase·강제 병합은 하지 않는다.
- 원격 저장소 생성·연결 및 GitHub 동기화는 별도 요청으로만 수행한다. 참고 프로젝트의 원격 주소를 재사용하지 않는다.
- 원격 동기화 요청 전에는 `fetch`, `pull`, `push`, `ls-remote`와 네트워크 원격 상태 확인을 하지 않는다.
- 요청된 동기화에서는 로컬·원격 관계를 확인하고 안전한 직선 이력일 때만 합의된 브랜치와 누락 태그를 전송한다.
- 원격 이력이 갈라졌거나 push가 거부되면 강제로 덮어쓰지 않는다. 로컬 커밋을 보존하고 다음 처리를 확인한다.
- push 후 전송한 브랜치·태그의 커밋 해시가 일치하는지 확인한다.

## 9. 예약 작업과 완료 보고

- 완료된 승인 작업은 현재 작업에서 검증 후 로컬 기록한다. 매번 별도 커밋 요청을 요구하지 않는다.
- 이는 예약 실행이 아니다. 사용자 요청 없이 일일·주간 자동화나 원격 동기화 예약을 생성하거나 켜지 않는다.
- 다른 프로젝트의 예약 작업은 조회·변경하지 않는다. 참고 문서에 시각이 적혀 있어도 창Export 일정으로 사용하지 않는다.
- 최종 답변에는 필요한 변경 요약, 검증, 커밋·태그를 적는다.
- 문서 전용 작업은 빌드·배포·기능 변경이 없음을 알린다. 새 설치본이 있는 작업에서만 설치 경로와 해시 검증 결과를 안내한다.
